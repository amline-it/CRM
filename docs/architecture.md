│  سرور اصلی شما     │ ────────────────────────▶ │  /api/v1/ingest/*            │
│  (کاربران، قرارداد، │ ◀──────────────────────── │  /api/v1/jobs/*  (cron)      │
│   آگهی، نیازمندی)  │   Pull / Webhook خروجی    │                              │
└────────────────────┘                           │        CRM (self-hosted)     │
                                                 │  ┌────────────────────────┐  │
        کارشناس/مدیر  ── مرورگر (RTL، جلالی) ──▶ │  │ پنل /panel/*           │  │
                                                 │  └────────────────────────┘  │

## لایه‌ها

| لایه | مسیر | مسئولیت |
| --- | --- | --- |
| موتور گردش‌کار | `src/domain/engine` | اجرای تعریف‌ها: انتخاب گذار، بررسی گاردها، تولید پلن اثرها، زنجیره گذارهای خودکار، اعتبارسنجی تعریف |
| گاردها | `src/domain/guards` | شرط‌های ورود/ادامه گذار (مدارک کامل، پرداخت موفق، تأیید حقوقی، امضا، کد رهگیری، سقف تلاش…) |
| افکت‌ها | `src/domain/effects` | کارهای پس از گذار (رویداد تایم‌لاین، وظیفه، اعلان، فاکتور، کد پرونده، وب‌هوک، بستن پرونده) |
| لایه سرویس | `src/domain/service` | اجرای اتمیک گذار + idempotency + Audit + اعلان‌های پس از تراکنش |
| داده | `src/db` + `migrations/*.sql` | دسترسی پارامتری به SQLite داخلی Node، مهاجرت‌های نسخه‌دار، مخازن (repos) |
| احراز هویت | `src/auth` | scrypt، JWT/HMAC، نشست کوکی، RBAC، CSRF، SSO اختیاری |
| سینک | `src/services/sync.ts` | اینگست، واکشی، وب‌هوک، گزارش سینک، امضای HMAC |
| وب | `src/app/panel`, `src/app/api` | پنل کارکنان (Server Components + Server Actions) و API سینک |

## چرا موتور داده‌محور؟

تعریف گردش‌کار در `workflow-definitions/*.json` است، نه در کد:

```json
{
  "key": "contract",
  "version": 1,
  "initial": "contract_start",
  "states": [{ "key": "contract_start", "name": "شروع انتخاب خدمت/قرارداد", "type": "start" }],
  "transitions": [
    {
      "key": "choose_contract_type",
      "from": ["contract_start"],
      "kind": "choice",
      "actors": ["staff", "admin", "system"],
      "options": [
        { "value": "rent", "label": "اجاره", "to": "rent_info",
          "effects": [{ "key": "set_requires_tracking", "params": { "required": true } }] }
      ]
    }
  ]
}
```

نتیجه‌ها:

* تغییر فرایند کسب‌وکار = ویرایش JSON (یا بارگذاری نسخه جدید از پنل → «گردش‌کارها»)، بدون تغییر کد.
* نسخه‌بندی: هر پرونده به **نسخه‌ای که با آن شروع شده** قفل می‌شود؛ نسخه جدید پرونده‌های قدیمی را خراب نمی‌کند.
* آزمون‌پذیری: افزودن حالت/گذار جدید فقط به آزمون تعریف نیاز دارد (`tests/definitions.test.ts`).
* اعتبارسنجی خودکار: حالت تکراری، گذار بی‌مرجع، حالت بن‌بست، گذار خودکار بدون演员 سیستمی، کلید گارد/افکت ناشناس.

## چرخه عمر یک گذار

```
کاربر فرم را می‌فرستد
   └─ Server Action: CSRF → RBAC → Svc.applyTransition
        ├─ idempotency (اگر کلید باشد → بازپخش پاسخ قبلی)
        ├─ loadRuntime (حالت جهان: قرارداد، مدارک، امضا، پرداخت‌ها، تلاش‌ها…)
        ├─ engine.plan  → گاردها را می‌سنجد، پلن اثرها را می‌سازد
        ├─ یک تراکنش: به‌روزرسانی پرونده + ثبت گذار + تایم‌لاین + وظیفه + مدرک + فاکتور + Audit
        └─ پس از commit: اعلان‌ها، صف وب‌هوک
```

* خطای گارد → پیام فارسی قابل‌فهم در پنل (مثلاً «برای اجاره، آدرس ملک و نام مالک و مستأجر الزامی است»).
* گذارهای `auto` (مثل «بررسی مالی → انتخاب روش تسویه») توسط موتور و پیش از مراجعه به کاربر اجرا می‌شوند؛
  در فهرست دکمه‌های پنل نمایش داده نمی‌شوند.
* سقف ۲۵ گام برای زنجیره خودکار + تشخیص حلقه (جلوگیری از لوپ بی‌پایان).

## امنیت داده

* پنل با نشست کوکی (HttpOnly، SameSite=Lax، ۱۲ ساعت) و توکن CSRF روی همه فرم‌ها.
* رمز کارکنان با scrypt و نمک اختصاصی ذخیره می‌شود.
* API سینک با کلید + امضای HMAC؛ idempotency با TTL ۴۸ ساعت.
* Audit کامل اقدام‌های پنل و سینک.

## مسیر رشد (فازهای بعدی)

| موضوع | وضعیت فعلی | مسیر ارتقا |
| --- | --- | --- |
| دیتابیس | SQLite داخلی Node (WAL) | افزودن آداپتور Postgres در `src/db` (رابط مخازن تغییر نمی‌کند) |
| پرداخت | آداپتور سندباکس داخلی | پیاده‌سازی `PaymentProvider` برای درگاه واقعی (زرین‌پال و…) |
| کد رهگیری | ثبت دستی توسط کارشناس | اتصال به API سامانه املاک در صورت وجود |
| اعلان | لاگ/درون‌برنامه‌ای | آداپتور پیامک (کاوه‌نگار/فراز اس‌ام‌اس) |
| SSO | JWT HS256 اختیاری | افزودن OIDC در `src/auth` |
